# Add a passphrase to an existing Tauri updater key — without stranding every install

## The situation that makes this urgent

The Tauri updater signing keypair gets generated once, early, usually with an
empty password because that's the path of least resistance (`--ci`, or just
pressing Enter). From then on the secret key sits at `~/.tauri/<app>.key` and
the release script passes `TAURI_SIGNING_PRIVATE_KEY_PASSWORD: ''`.

Threat shape, stated plainly: **without** that key, an attacker who gains write
access to your release bucket can only *deny* updates — every installed client
verifies signatures against a pubkey compiled into the binary. **With** the
key, it's silent RCE on the entire install base: a signed malicious artifact is
accepted and (with `installMode: "passive"`) installed with no user
interaction. The whole update channel's security reduces to "who can read one
file" — and with an empty password, *reading the file is having the key*.
Every backup of the file carries identical power: a synced folder, a password
manager entry with the key text, an old laptop.

## The trap — the reason this article exists

**Do not fix this by regenerating the keypair with a password.** The public
key is compiled into every binary you have ever shipped. A new keypair means
every existing install can verify no future update — they are stranded on
manual downloads forever, silently (update-check failures are deliberately
quiet). Nothing in `tauri signer` warns you about this, and
`tauri signer generate -f` will happily overwrite the key that your install
base depends on.

The safe direction keeps the **same keypair** and only encrypts the secret key
at rest.

## The fix: the Tauri key file is just base64 of a minisign secret key

The Tauri CLI has no rekey command (`tauri signer` = `generate` + `sign`
only). But the key file is a single-line base64 wrapper around a standard
minisign secret key, and C minisign has `-C` — change/set the secret key's
password in place:

```bash
# work on a COPY; original untouched until everything below passes
mkdir rekey && cp ~/.tauri/myapp.key rekey/original.key.b64
base64 -d < rekey/original.key.b64 > rekey/decoded.key   # 2 lines: untrusted comment + key data

minisign -C -s rekey/decoded.key   # prompts: current pw (Enter if empty), new pw twice

base64 -w0 < rekey/decoded.key > rekey/rekeyed.key.b64   # same single-line format Tauri expects
```

Cross-implementation compatibility is real, not assumed: a key generated by
the Tauri CLI (rust-minisign) was rekeyed by **C minisign 0.12** and consumed
again by **Tauri CLI 2.10.1** — both directions worked (measured 2026-07-29).

## Verify BEFORE swapping the live key — all three, in this order

1. **Negative:** signing with the old empty password must now FAIL.
   `TAURI_SIGNING_PRIVATE_KEY="$(cat rekey/rekeyed.key.b64)" TAURI_SIGNING_PRIVATE_KEY_PASSWORD='' pnpm tauri signer sign testfile`
   → expect `Wrong password for that key`. If it signs, the rekey didn't take.
2. **Positive:** sign a test file with the passphrase **through the same
   channel your release pipeline uses** (env vars, not `-p` on the CLI — see
   the bug note below for why the channel matters).
3. **Keypair intact:** the produced `.sig` is base64 of a `.minisig`; decode it
   and verify against the ORIGINAL pubkey — the exact string in
   `tauri.conf.json` that shipped inside your binaries:
   `base64 -d < testfile.sig > testfile.minisig && minisign -Vm testfile -p <decoded original pubkey>`
   This is the line that proves no install gets stranded.

Only then replace `~/.tauri/myapp.key` with the rekeyed file.

## The env-password bug report that almost derails the plan

[tauri-apps/tauri#13485](https://github.com/tauri-apps/tauri/issues/13485)
reports that a key password supplied via `TAURI_SIGNING_PRIVATE_KEY_PASSWORD`
fails ("Wrong password for that key") while the CLI flag works — reported on
2.5.1, untriaged. Measured 2026-07-29 on CLI 2.10.1: **does not reproduce**;
env-supplied password signs fine. Cheap way to check your own version before
trusting a release run: `tauri signer sign` honors the same two env vars as
the bundler, so it's a 2-second repro harness.

## Release-pipeline consequences

- **Prompt hidden, then fail-fast test-sign before the build.** Read the
  passphrase with echo off, then sign a throwaway temp file (~2s) *before*
  version stamping and the minutes-long build, so a typo fails instantly.
- **`||` not `??` for the env fallback.** An empty-string
  `TAURI_SIGNING_PRIVATE_KEY_PASSWORD` is the *legacy no-passphrase config*,
  not a valid password — it must fall through to the prompt.
- **The passphrase is now exactly as unlosable as the key.** Losing it strands
  every install just like regenerating would. Put it in the password manager
  BEFORE running `minisign -C`, named by product ("MyApp — updater signing key
  passphrase"), with a note saying what it unlocks and that loss is
  unrecoverable.

## Rotate every copy of the old file — they all still carry full power

The rekey protects the live file; it does nothing for copies made earlier.
Hunt them deliberately:

- **Password managers keep version history.** Editing the entry that holds the
  old key text preserves the old text underneath. Delete the entry, create a
  fresh one, empty the manager's trash.
- **Cloud-synced folders keep recycle bins AND per-file version history**, and
  a delete-then-recreate of the same filename can be coalesced by the sync
  client into a "modify" that preserves history (observed with OneDrive
  semantics — check the file's version history, not just the recycle bin).
  Also verify whether the folder is *actually syncing* before assuming cloud
  exposure: a folder named OneDrive with no signed-in account is just a local
  folder.
- **Disk scan beats memory.** `find ~ -iname "*.key"` plus a content check
  (minisign files decode from base64 prefix `dW50cnVzdGVkIGNvbW1lbnQ`) found a
  forgotten 9-day-old copy the owner was sure didn't exist.
- Accepted residuals worth naming rather than hand-waving: OS shadow copies
  (need local admin — usually inside your already-game-over boundary) and SSD
  unallocated remnants (out of threat model for a non-targeted solo dev).
